Long prompts

Coding agents on a large codebase, research over documents and agents with a lot of saved context send long prompts and get short answers back, so processing the prompt (prefill) can take longer than writing the reply. Real coding-agent traffic is longer still: in TraceLab's traces of Claude Code and Codex sessions, a typical step resends about 120K tokens of history, adds under 1K new tokens and writes about 250, and 96% of prompt tokens were already in the server's cache. These charts use one user unless they say otherwise.

Reading these results

  • Wall power covers the whole machine: CPU, memory, fans and power-supply losses as well as the accelerators. QuietBox 2 draws several hundred watts even when idle, so its efficiency mostly follows its speed.
  • On the Sparks, the dense models (Qwen3.6 27B, Devstral, Gemma 4, Muse Glimmer) ran in BF16. An FP8 or NVFP4 build would read fewer bytes per token and likely be faster and more efficient there.
  • QuietBox 2 runs tt serve bundles; the Sparks run vLLM in NVIDIA's container; Macs run 4-bit MLX builds with mlx_lm.server. Same models, different builds, precisions and kernels.
  • The Intelligence Index scores come from Artificial Analysis’s published runs, not from these machines. Most are for reasoning mode, which writes more tokens per answer, so energy per answer is higher than energy per token suggests. These benchmarks used a fixed output length.
  • DeepSeek V4.1 Flash on QuietBox 2 and Gemma 4 with many users look slower than they should be and are under investigation.
  • Two DGX Sparks run one copy of gpt-oss-120b split across both machines over the direct QSFP link, and both plugs are summed.
  • The default QuietBox 2 builds of gpt-oss-20b and Qwen3.6 35B A3B run on one Blackhole chip; their 4-chip builds spread the same model over all four.
  • Tenstorrent p150 is one p150a card (one Blackhole chip, 32 GB) in a desktop with a 6-core Ryzen 5 5500 on PCIe 3.0, running the same gpt-oss-20b and Qwen3.6 35B A3B bundles as QuietBox 2's single-chip builds on Talos Linux and Kubernetes (Tenstorrent's tt-operator) instead of Ubuntu. On QuietBox 2 that stack matched Ubuntu on decode speed and power under load. The p150's wall power is from the power test only, measured with the operator's telemetry collector off; the box idles at 98 W. Decode speed matches a QuietBox 2 chip, at about half the wall power. Qwen3.6 was only run with one user.
  • Qwen3 8B is the small-model comparison: the same 8B dense model on four single-accelerator machines, all on Talos Linux and Kubernetes. Tenstorrent n300 (two Wormhole chips, 24 GB) and Quadro RTX 6000 (Turing, 24 GB) sit in the same Ryzen 5 5500 desktop as the p150. The Tenstorrent cards run Tenstorrent's tt-transformers build through vLLM; there is no official p150 entry for this model, so the p150 ran the n300 entry adapted for one Blackhole chip. The RTX 6000 runs vLLM 26.04 in fp16 (Turing has no bf16), which leaves room in 24 GB for only one 40K-token request at a time; the Spark runs vLLM 26.04 in bf16. Wall power for the Tenstorrent cards is from the power test only, with the telemetry collector off; the RTX 6000 and Spark have wall power for every test. The n300 is missing the 32K-token test, and 32 of its 96 requests failed with 32 users in the users test.
